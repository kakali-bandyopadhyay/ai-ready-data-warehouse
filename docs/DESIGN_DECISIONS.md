# Design decisions

These records describe the runnable PostgreSQL implementation and the configured, not yet measured, Phase 2 cloud targets. Synthetic data is used throughout.

## ELT over ETL

**Decision:** model the loaded raw tables as dbt `source()` relations so they can carry source freshness definitions, and load them with an explicit `dbt seed` step before freshness checks or builds. A `source()` reference records source metadata but does not create a DAG edge to a dbt seed node, so `dbt build` alone cannot guarantee the raw tables exist on a clean database. Every build therefore uses `--exclude resource_type:seed`; changed seed data is reloaded explicitly before the snapshot-dependent build. This keeps raw seed tables available for inspection and transformation logic in versioned SQL models. Implemented by [`pipeline/run.py`](../pipeline/run.py), source definitions in [`sources.yml`](../models/sources.yml), and `models/`.

## Incremental fact strategy

**Decision:** use PostgreSQL merge materialization keyed by stable holding and transaction IDs. The transaction fact re-reads a 90-day ingestion-time overlap to catch recent late-arriving records. Holdings re-reads a 30-day date overlap. The runner explicitly seeds before source freshness and the initial seed-excluded build, promotes/reloads the changed company seed, then builds again to advance SCD2 and repeats that build to compare fact counts/checksums. The local sequence completed successfully; see [`FINDINGS.md`](../FINDINGS.md). The overlap is a documented lateness bound; older changes require a full refresh. Implemented in [`fct_holdings_daily.sql`](../models/marts/fct_holdings_daily.sql), [`fct_transactions.sql`](../models/marts/fct_transactions.sql), and [`run.py`](../pipeline/run.py).

## PostgreSQL build concurrency

**Decision:** run dbt with one thread for the local PostgreSQL profile. PostgreSQL view replacement takes strong locks on dependent rewrite rules, and parallel dbt rebuilds of shared staging views can deadlock. This serialization addresses the observed third-build deadlock; it is separate from the slow `ai_company_profile` query and does not by itself establish a profile timing improvement. Implemented in the temporary profile generated by [`run.py`](../pipeline/run.py).

## AI company profile query shape

**Decision:** build the company profile from the current physical dbt snapshot and join one latest KPI row per company. The prior path joined `stg_companies` to `stg_company_kpis`; the KPI model also depended on the companies staging view, expanding that view again under the profile join. The profile build's logged 76–102 seconds for 400 rows is disproportionate to the result size; the query has no explicit correlated subquery or cross join, so the duplicated view dependency and its window/joins are the avoidable SQL work. The revised path filters `company_history` to its current version and materializes KPI staging as a table with one row per `company_id`. This removes the repeated company-view expansion and bounds the profile join to one current company and one KPI per company. The same change is applied to the local Postgres and cloud project models. The optimized timing still needs measurement against a running database.

## SCD Type 2

**Decision:** use a dbt timestamp snapshot keyed by company ID with source ingestion time as the update marker. Preserve changed company versions and derive a surrogate company key from dbt's snapshot key. The current row has no end timestamp. Implemented in [`company_history.sql`](../snapshots/company_history.sql) and [`dim_company.sql`](../models/marts/dim_company.sql).

## Cloud physical design (Phase 2)

Snowflake's cloud project applies a clustering key to `fct_holdings_daily` for repeated date/company filters. The runbook starts with an XS warehouse and 60-second auto-suspend; a 10-credit monthly resource monitor and account budget alert add guardrails where account privileges allow. The measurement script records load/build timings, row counts, and visible warehouse credits. No cloud result has been recorded here.

Databricks uses Delta tables and supports a serverless SQL warehouse. Liquid clustering is configured on `fct_holdings_daily`. A small warehouse and 5-minute auto-stop plus workspace budget alerts limit idle exposure. Unity Catalog tags are opt-in and require the appropriate privileges; model documentation carries owner and classification metadata. The measurement script queries visible DBUs. No cloud result has been recorded here.

## Delta and warehouse tables

Delta Lake is the Databricks storage layer and brings transaction log semantics to data files. Snowflake uses managed warehouse tables. The cloud-specific models live in [`cloud_project/`](../cloud_project/); PostgreSQL remains the local and CI target.

## pgvector and platform vector search

**Decision:** use pgvector and HNSW cosine distance for the runnable local demo. It keeps retrieval rows and provenance next to relational data. Cloud tables include a Snowflake `VECTOR(FLOAT, 8)` or Databricks `ARRAY<FLOAT>` embedding placeholder. The cloud build does not generate embeddings or execute semantic vector queries; those platform demos remain documented, not run. Implemented locally in [`ai_text_chunks.sql`](../models/ai_ready/ai_text_chunks.sql) and [`vector_search.py`](../pipeline/vector_search.py).

## Cost controls

Local PostgreSQL is containerized and stopped when idle. Cloud runbooks specify the smallest suitable warehouse, auto-suspend/auto-stop, explicit teardown, and budget alerts before any build. No cloud resources were created or tested from this environment.

## Relational system of record; graph as a later add-on

**Decision:** normalized source keys and dimensional facts are the Phase 1 system of record. Relationship traversal can be added as a separate graph projection in Phase 3 if separately approved. No graph database or graph models are included now.
